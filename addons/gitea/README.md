# `gitea/` — per-project Gitea instance (internal tooling)

This directory holds the docker-compose overlay and first-run bootstrap
script for <name>'s **Gitea** instance. This is **internal tooling** — the
Gitea instance is used during development to manage branches and PRs from
the bot pipeline. The final shipped project goes to the company's real git
host (GitHub, GitLab, etc.) with a clean history. Gitea is a lightweight
self-hosted git server (written in Go, ~300MB resident) that handles:

- **Hosting the branches** that dispatched sub-agents push after finishing
- **Opening pull requests** via the Gitea REST API (from `bot/tools/gitea.py`)
- **The review UI** for humans to look at diffs / approve / comment
- **Merging PRs** after the review agent (or a human) approves them
- **Keeping the review history** audit-able in one place per project

## Why one Gitea per project?

Each scaffolded project gets its own container so:

- The bot's PR workflow stays fully self-contained
- No cross-project bleed — branches, tokens, reviews stay isolated
- Starting / stopping a project also stops its git server
- Fresh database, fresh admin, fresh bot user per project

**Resource cost:** ~300MB RAM per project when idle, ~1GB cap in the
compose. If you run many projects and want to consolidate, point every
project's `GITEA_URL` at a shared upstream Gitea — the scaffold doesn't
hardcode the URL, so both patterns work.

## Contents

```
gitea/
├── docker-compose.gitea.yml  compose overlay with Gitea service
├── bootstrap.sh              first-run automation (admin, bot user, token, repo)
├── README.md                 this file
└── data/                     SQLite db + git repos + logs (gitignored)
```

## First run

```bash
# 1. Bring up Gitea
make gitea

# 2. Bootstrap (creates bot user + API token + repo + seeds main branch)
make gitea-bootstrap

# 3. Optional: enable Actions only for trusted workflows
make gitea-runner
```

The bootstrap script is idempotent — safe to rerun if something fails.

`make gitea-runner` is deliberately separate. The runner mounts the host Docker
socket, which grants host-level Docker control even though job containers are
configured as non-privileged. Do not enable it for untrusted repositories,
pull requests, actions, or workflow definitions.

## Normal operation

```bash
make gitea         # start gitea
make gitea-logs    # follow gitea logs
make gitea-down    # stop gitea (data persists in gitea/data/)
```

## Integration with the bot

After the bot dispatches a sub-agent via `dispatch_agent.py` and the agent
finishes successfully:

1. Bot pushes the sub-agent's branch to Gitea via the HTTPS remote with
   the token stored in `.env`
2. Bot opens a PR via `POST /api/v1/repos/<owner>/<repo>/pulls`
3. PR URL lands in the sub-agent run memory (`memory/sub_agent_runs/`)
4. If `GITEA_AUTO_REVIEW=true`, the bot immediately calls the `review_pr`
   tool, which fetches the diff, queries memory + design-advisor for context, runs
   an LLM review, and either merges / requests changes / rejects

Sub-agents never hold the Gitea token. The token stays with the
orchestration bot — the sandbox whitelist (`AGENT_SANDBOX_FORWARD_ENV`)
does not include `GITEA_TOKEN`. All Gitea writes happen OUTSIDE the
sandbox. This matches the security model in AGENTS.md §22.

## Config

All configuration lives in `.env` (gitignored). The bootstrap script
populates these:

```bash
GITEA_URL=http://127.0.0.1:3030
GITEA_API_URL=http://127.0.0.1:3030/api/v1
GITEA_HTTP_PORT=3030
GITEA_SSH_PORT=2222
GITEA_OWNER=<name>-bot
GITEA_REPO=<name>
GITEA_BOT_USER=<name>-bot
GITEA_BOT_PASSWORD=<auto-generated>
GITEA_TOKEN=<auto-generated>

# Review agent behavior (optional)
GITEA_AUTO_REVIEW=false              # run review_pr after each dispatch
GITEA_AUTO_MERGE_CONFIDENCE=high     # min confidence for auto-merge
```

**Running multiple projects on the same host?** Give each project a
different `GITEA_HTTP_PORT` / `GITEA_SSH_PORT` in its `.env`. The compose
overlay reads from the env, so there's no conflict.

## Remote access via reverse proxy

By default the Gitea container binds to `127.0.0.1` only — it's not
reachable from outside the host. To make the sign-in page reachable remotely
(so authorized humans can review PRs, the bot's IRC links are clickable, and
webhooks can reach it), use the operator's central Caddy reverse proxy.
Repositories remain private and Gitea requires authentication before showing
the web UI or repository content.

### The convention

Every scaffolded project's Gitea is reachable at a predictable URL:

```
https://<slug>-git.<your-public-domain>
```

Where `<slug>` is the project name — the same slug used for the IRC
channel `#<slug>` and the project directory. If you scaffold
`rsi-backtest`, its Gitea is at `https://rsi-backtest-git.<your-domain>`.
One slug everywhere.

### How to expose it

1. **Add a wildcard DNS record** for your public zone:
   `*.<your-public-domain>` → your host IP. Or add one A record per
   project if you prefer explicit.

2. **Paste the snippet** from `gitea/caddy.example` into your central
   Caddyfile (the operator's existing `~/caddy-proxy/Caddyfile` or
   equivalent). The snippet has placeholders (`<name>`, `<GITEA_PUBLIC_DOMAIN>`,
   `<GITEA_HTTP_PORT>`) that you replace with real values before saving.

3. **Set the env vars** in this project's `.env`:

   ```bash
   GITEA_PUBLIC_DOMAIN=your-dev-zone.example
   GITEA_PUBLIC_URL=https://<name>-git.your-dev-zone.example
   ```

   When `GITEA_PUBLIC_URL` is set, the compose file propagates it to
   Gitea's `ROOT_URL` so clone URLs, web links, and webhook payloads all
   point at the public address instead of `http://127.0.0.1:3030`.

4. **Reload Caddy** and restart Gitea so `ROOT_URL` takes effect:

   ```bash
   # On the operator host, reload the central Caddy
   caddy reload --config ~/caddy-proxy/Caddyfile

   # In the project directory, restart Gitea so the new ROOT_URL applies
   make gitea-down && make gitea
   ```

5. **Verify** by visiting `https://<name>-git.<your-domain>` in a
   browser. Log in with the bot user from `.env`.

### Bot IRC link formatting

Once `GITEA_PUBLIC_URL` (or just `GITEA_PUBLIC_DOMAIN`) is set,
`bot/tools/gitea.py::pr_url(index)` returns the public URL instead of
`127.0.0.1`. So when the bot announces a new PR in IRC, the link is
clickable from anywhere. Resolution order:

1. `GITEA_PUBLIC_URL` (full URL, highest priority)
2. `https://<repo>-git.<GITEA_PUBLIC_DOMAIN>` (zone-only convention)
3. `GITEA_URL` (`http://127.0.0.1:3030`, localhost fallback for dev)

### Committed-config safety rule

**The actual domain never appears in committed files.** Every reference
uses placeholders like `<GITEA_PUBLIC_DOMAIN>` or `<your-public-domain>` —
real domains live only in `.env` and `LOCAL.md` (both gitignored).
`yala.sh` runs a leak check after bootstrap to catch
accidental committed references.

## Pointing at an operator-wide shared Gitea instead

If you want to consolidate, skip `make gitea` entirely and just set the
env vars manually in `.env`:

```bash
GITEA_URL=https://gitea.internal
GITEA_API_URL=https://gitea.internal/api/v1
GITEA_OWNER=shared-org
GITEA_REPO=<name>
GITEA_TOKEN=<your-upstream-token>
```

The bot's tools don't care whether Gitea is local or remote.

## Security

- Gitea binds to `127.0.0.1` only. External access is the operator's
  responsibility via reverse proxy (AGENTS.md §2).
- `DISABLE_REGISTRATION=true` — no random signups.
- `REQUIRE_SIGNIN_VIEW=true` — anonymous users cannot browse the web UI or
  repository content, including when a reverse proxy exposes the sign-in page.
- Repos are created as **private** by default. Rerunning bootstrap also
  reconciles the scaffold-managed repository back to private.
- Health checks use `/api/healthz`, which remains available without granting
  anonymous access to repository APIs.
- `INSTALL_LOCK=true` — the interactive install wizard is bypassed.
- Bot password is auto-generated on first bootstrap.
- Data (SQLite DB + git repos) lives in `gitea/data/` which is gitignored.

**Never commit `.env` — it contains `GITEA_TOKEN` and `GITEA_BOT_PASSWORD`.**
The scaffold's `.gitignore` already excludes it; `gitleaks` will catch
accidental leaks.

## Unseating a misbehaving review agent

If the review agent starts merging things it shouldn't:

```bash
# 1. Flip off auto-review
echo "GITEA_AUTO_REVIEW=false" >> .env
make bot-down && make bot

# 2. Review the memory/pr_reviews/ directory to see what it merged
ls memory/pr_reviews/

# 3. Revert problematic merges via git revert (on main) or manually close PRs
```

The reviews are captured in `memory/pr_reviews/`, so you can audit every
decision the agent made.
